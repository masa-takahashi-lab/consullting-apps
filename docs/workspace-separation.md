# ワークスペース分離設計 — 株式会社ふもと / 個人事業

法人設立にともない、Mac 上の作業環境を法人と個人で完全に分離するための設計と手順。

## 中核となる設計判断

> **文書のフォルダ階層をローカルに作らない。**

SharePoint には既にフォルダ体系がある。同じ階層をローカルにも作れば、
「どちらが最新か分からない」二重管理が必ず生まれる。
滝川市案件が個人 Drive と法人 SharePoint の両方に存在している現状が、
まさにその失敗例である。

したがってこのセットアップは、OneDrive が同期している SharePoint ライブラリ実体への
**リンクを張るだけ**で、文書用のディレクトリは一切作らない。

この判断には副次的だが重要な効果がある。
**セットアップスクリプトが SharePoint の構成を知っている必要がなくなる。**
構成は常に SharePoint 側が正であり、ローカルは同期実体を参照するだけなので、
SharePoint 側でフォルダを増減しても、ローカルとズレることが原理的に起きない。

## なぜフォルダを分けるだけでは足りないか

「分ける」対象は 4 層ある。フォルダだけ分けても、コミットが個人メールで飛んだり、
会社資料が個人 Drive に同期されたりすれば分離は成立しない。

| 層 | 分けないと起きること | 本設計での対処 |
|---|---|---|
| ローカルフォルダ | どちらの資産か判別できない | ルートを 2 つに固定 |
| Git identity | 会社のコミットに個人メールが残る | `includeIf` で自動切替 |
| クラウド同期 | 会社資料が個人 Drive に流れる | 同期実体を各ルートへリンク |
| GitHub | 会社コードが個人 org に残る | 法人 Organization へ移管 |

## 1. ローカルフォルダ構成

ルートは 2 つだけ。**この 2 つの外に案件ファイルを置かない**ことが唯一の運用ルール。

```
~/fumoto-inc/                              法人 — ここから下は全部会社
├── <サイト名> - Documents  →  リンク       SharePoint 同期実体（正）
├── OneDrive                →  リンク       OneDrive 同期実体（正）
├── 40_コード/                              ローカル実体（正は GitHub 法人 org）
├── _local/                                 一時作業（消えてよいもの専用）
├── .gitconfig                              法人の Git identity
└── README.md                               境界ルール

~/personal/                                個人事業 — ここから下は全部個人
├── GoogleDrive             →  リンク       Google Drive 同期実体（正）
├── 40_コード/                              ローカル実体（正は masa-takahashi-lab）
├── _local/
├── .gitconfig
└── README.md
```

リンク名は SharePoint / OneDrive が付けたライブラリ名をそのまま使う。
こちらで読みやすい別名を付けると、SharePoint 上の呼び名と食い違って混乱するため、
**あえて元の名前を維持している**。

### 実体を作ってよい場所

| 場所 | 実体を作ってよいか | 正 |
|---|---|---|
| リンク配下（SharePoint / OneDrive / Drive） | ○ | クラウド側 |
| `40_コード/` | ○ | GitHub |
| `_local/` | ○（消えてよいものだけ） | なし |
| それ以外 | **×** | — |

### 迷ったときの判断基準

> ふるさと納税制度に関する自治体サポートに関わるものは、
> **たとえ個人名義で受注した経緯があっても法人側に置く。**

## 2. Git identity の自動切替

`~/.gitconfig` に `includeIf` を追記し、ディレクトリごとに author を切り替える。
手動での `git config user.email` は不要になり、設定忘れによる混線が構造的に起きなくなる。

```gitconfig
[includeIf "gitdir:~/fumoto-inc/"]
	path = ~/fumoto-inc/.gitconfig
[includeIf "gitdir:~/personal/"]
	path = ~/personal/.gitconfig
```

検証済みの挙動:

| リポジトリの場所 | コミットに使われる identity |
|---|---|
| `~/fumoto-inc/` 配下 | `masanori.takahashi@fumoto-inc.co.jp` |
| `~/personal/` 配下 | `masa.takahashi888@gmail.com` |
| どちらでもない場所 | 従来のグローバル設定のまま |

確認方法:

```bash
cd ~/fumoto-inc/40_コード/<任意のリポジトリ>
git config user.email    # → masanori.takahashi@fumoto-inc.co.jp
```

## 3. クラウド同期の分離

| | 法人 | 個人 |
|---|---|---|
| 正 (source of truth) | SharePoint `fumoto2026` / OneDrive | Google Drive |
| アカウント | masanori.takahashi@fumoto-inc.co.jp | masa.takahashi888@gmail.com |
| ローカルからの参照 | `~/fumoto-inc/<ライブラリ名>` | `~/personal/GoogleDrive` |

macOS の OneDrive は以下の命名で同期実体を作る。スクリプトはこれを検出して分類する。

| 同期フォルダ名 | 種別 | リンク先ルート |
|---|---|---|
| `OneDrive-<組織名>` | 個人 OneDrive。**ショートカット方式ではここに各チャネルが並ぶ** | 法人 |
| `OneDrive-SharedLibraries-<組織名>` | SharePoint ライブラリを「同期」した場合（配下に 1 サイト 1 フォルダ） | 法人 |
| `GoogleDrive-<メールアドレス>` | Google Drive | 個人 |

分類できない同期フォルダがあった場合は警告を出すだけで、勝手にリンクしない。

### 同期方式は「ショートカットの追加」を使う

運用ルール第4版に次の定めがある。

> **同期** — 「同期」ではなく「OneDrive へのショートカットの追加」を使う
> （PC の容量を消費しない）

ショートカット方式では、SharePoint の各チャネルが `OneDrive-<組織名>/` の直下に並ぶ。
`OneDrive-SharedLibraries-*` が存在する場合は「同期」ボタンを使った状態なので、
スクリプトが警告を出す。動作はするが、規程どおりの状態ではない。

### 同期実体の確認

構成を触らずに実物だけ見たいときは:

```bash
bash scripts/setup-workspace.sh --show-sync
```

## 4. GitHub リポジトリの分離

### 現状

すべてのリポジトリが個人アカウント配下の `masa-takahashi-lab` にある。
このリポジトリ (`consullting-apps`) も同様。

### 手順

1. GitHub で法人用 Organization を作成する（例: `fumoto-inc`）
   - Settings → Organizations → New organization
   - 支払い情報は法人名義のものを登録する
2. 会社の資産にあたるリポジトリを移管する
   - 対象リポジトリの Settings → General → Danger Zone → **Transfer ownership**
   - 移管後も旧 URL からはリダイレクトされるため、ローカルの remote 変更は急がなくてよい
3. ローカルの clone 先を `~/fumoto-inc/40_コード/` に移す
4. remote URL を更新する

```bash
git remote set-url origin https://github.com/fumoto-inc/<repo>.git
```

### 判断が必要なもの

`consullting-apps` は現在このセットアップ手順そのものを格納しているが、
中身が会社の業務システムになるなら法人 org へ移管対象になる。
個人の実験リポジトリとして残すなら個人側に置いたままでよい。

## 5. 滝川市案件の二重管理について

### 現状（調査で確認済み）

同じ案件の資料が 2 箇所に存在している。

| 場所 | 内容 |
|---|---|
| Google Drive（個人） | `滝川市向け資料` — 提案書 v5.1〜Final、覚書、契約書 |
| SharePoint（法人） | `/sites/-10_` → `01_2026_ふるさと納税改革支援` |

### 決定した方針と、それが抱える規程上の問題

**法人 SharePoint を正とし、個人 Drive 側にも当面コピーを残す**と決めた。
ただし全走査の結果、この判断は自社規程に抵触することが判明している。

運用ルール第4版:

> **二重管理の禁止** — Google Drive へのリンク貼付は行わない。
> SharePoint を唯一の正とする（文書管理規程 第3条）

さらに滝川市はプライベートチャネル `100_滝川市` に置かれており、
これは利益相反管理規程 B07 第7条にもとづき
「特定の1名だけ、特定の案件のファイルが見えない」状態を作るための構成である。
個人 Drive にコピーがあると、この権限の壁が迂回される。

暫定措置としても規程違反にあたるため、**早期の一本化を推奨する**。
当面残す場合も、下記ルールの遵守が最低条件になる。

移行リスクを避けるための暫定措置であり、恒久的な状態ではない。
二重管理は放置すると必ず「どちらが最新か分からない」事故になるため、
次のルールをセットで運用する。

- 更新は **必ず SharePoint 側に対して行う**
- 個人 Drive 側のコピーは **編集しない**（参照専用）
- この方針は `~/personal/README.md` にも記載してあり、開いた人が気づくようにしてある

### 解消の目安

法人側での運用が安定した時点で、個人 Drive のコピーを
アーカイブするか削除し、上記の注意書きも削除する。

## 5-2. Google Drive から SharePoint への移行

`scripts/migrate-drive-to-sharepoint.sh` で実行する。

```bash

bash scripts/migrate-drive-to-sharepoint.sh             # 実行
```

### なぜ API ではなくローカルコピーなのか

当初は Microsoft Graph API 経由での移行を試みたが、次の理由で断念した。

| 問題 | 内容 |
|---|---|
| アップロード上限 | 1 MiB。分割アップロード非対応。提案書（8.2 MB）等が原理的に移せない |
| バイナリの破損 | base64 を経由するため、大きいファイルほど転送中に壊れる（実際に失敗を確認） |

Mac には Google Drive と OneDrive の両方が同期されているため、
ローカルのファイルコピーであればサイズ無制限かつ破損なく移行できる。
実測で 8.2 MB / 3.2 MB のファイルがバイト単位で一致することを確認済み。

## 6. セットアップ手順

```bash
# 0. 同期フォルダの実物を確認する（何も作成しない）
bash scripts/setup-workspace.sh --show-sync

# 1. 何が起きるか確認する（何も作成しない）
bash scripts/setup-workspace.sh --dry-run

# 2. 問題なければ実行する
bash scripts/setup-workspace.sh
```

### スクリプトの安全性

検証済みの性質:

- **既存ファイルの移動・削除・上書きを一切行わない。** 作るだけ
- 何度実行しても結果が変わらない（冪等。2 回目は作成 0 件）
- `~/.gitconfig` を変更する前に `.bak-before-workspace-split` へ退避する
- リンク先が想定と異なる場合、リンクを張り替えず**警告して停止**する
- リンク位置に実体（フォルダ）が既にある場合も、**壊さず警告のみ**
- 分類できない同期フォルダには触れない

### 実行後にやること

1. Git identity が切り替わることを確認する（上記 2 の確認方法）
2. 棚卸しに出たリポジトリを `40_コード/` 配下へ手で移す
3. 法人 GitHub Organization を作成する（上記 4）

振り分けを自動化していないのは意図的な判断である。
どちらに属するかの判断は事業上の判断であり、ファイル名から機械的に決められない。

## 付録: 設計を差し替えた経緯

初版では、案件フォルダの階層（`00_プロジェクト管理` `10_受領・インプット資料` など）を
スクリプト内にハードコードしていた。これには 2 つの問題があった。

1. **実在しない階層が混入していた。** `20_分析・作業` `30_成果物` は SharePoint に存在せず、
   `40_交渉` を `40_交渉・契約` と改名し、法人運営側の階層
   （SharePoint 実物は `002_会社規程・台帳` `003_経理・税務` `連絡事項` `999_全般・雑談`）は
   全面的に一致していなかった。また `01_2026_ふるさと納税改革支援` という
   案件年度の階層が丸ごと抜けていた。
2. **そもそも把握が不完全だった。** 初版の構造把握はキーワード検索の結果であり全走査ではない。
   検索に引っかからないフォルダは見えていない。

ハードコードを直しても、把握が不完全である限り同じ誤りを繰り返す。
そこで「ローカルに階層を作らず同期実体を参照する」設計へ差し替えた。
これにより、スクリプトが構成を知らなくても正しく動くようになった。
